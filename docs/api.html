01 How it works

OpsTally Agent is a small desktop application that runs on the same machine, or same local network, as Tally Prime. It talks to Tally over Tally's own local XML gateway — the same interface Tally itself exposes for import and export — so nothing about your Tally setup has to change.

On a schedule you configure, the Agent polls Tally, works out exactly what changed since the last pass, and pushes each change as one signed JSON event to a single HTTPS endpoint you provide. Your system receives a steady stream of small, typed events instead of having to poll or diff anything itself.

Stock
Quantity, unit, sale & cost price
per-item, on change
Ledgers
Accounts, groups, GSTIN
per-account, on change
Vouchers
Invoices, receipts, payments, journals
per-voucher, on change or cancel

02 Security posture

The Agent opens no inbound port and runs no local server — there is nothing on your network for it to expose. All traffic is outbound, initiated by the Agent, to the one URL you configured. Nothing can reach your Tally data by contacting the Agent directly, because there is nothing listening on it.

Secret storage

Your webhook signing secret (prefixed whsec_) is generated on the Agent and stored on-device using OS-level encryption — it is never transmitted anywhere. Only the HMAC signature it produces is sent, over HTTPS, with every event.

03 Quick start

  1. Install OpsTally Agent on the machine running Tally Prime, or one with network access to it.
  2. Point it at Tally. Host and port default to localhost:9000; select which Tally company to sync.
  3. Set your webhook URL in the Agent's settings. The first time you do, the Agent generates a signing secret — copy it into your own environment as a secret, never into client-side code.
  4. Verify signatures on your endpoint before deploying it — see Verifying signatures.
  5. Send a test event. The "Send test event" button in the Agent fires a signed ping, confirming your endpoint, TLS, and signature check all work before any real data flows.
  6. Un-pause syncing. The Agent silently baselines what it sees first, then starts sending stock.updated, ledger.*, and voucher.* events as things actually change.

04 Verifying signatures

Every request carries an X-Tally-Signature header: the hex-encoded HMAC-SHA256 of the exact raw request body bytes, keyed with your webhook signing secret.

HeaderValue
Content-Typeapplication/json
X-Tally-Signaturehex HMAC-SHA256 of the raw body, using your secret
X-Tally-Eventevent type, e.g. stock.updated — matches the body's event field, so you can route before parsing JSON
X-Tally-Event-Idthis event's unique id — matches the body's id field
User-Agentopstally-agent/<version>
Node.js / Express
import { createHmac, timingSafeEqual } from 'node:crypto';

// Compute over the raw bytes -- do this before any JSON body parser touches the request.
function verify(rawBody, signatureHeader, secret) {
  const expected = createHmac('sha256', secret).update(rawBody).digest('hex');
  const a = Buffer.from(signatureHeader, 'hex');
  const b = Buffer.from(expected, 'hex');
  return a.length === b.length && timingSafeEqual(a, b);
}

app.post('/webhooks/opstally', express.raw({ type: 'application/json' }), (req, res) => {
  const signature = req.header('X-Tally-Signature') || '';
  if (!verify(req.body, signature, process.env.OPSTALLY_WEBHOOK_SECRET)) {
    return res.status(401).json({ error: 'invalid signature' });
  }
  const event = JSON.parse(req.body.toString('utf8'));
  // ... queue event.event / event.payload for processing, then respond fast:
  res.status(200).json({ ok: true });
});
Common mistake

Most frameworks parse JSON before your handler ever sees it, which re-serializes whitespace and byte order and silently breaks the signature. Mount this route with a raw body parser, not your default JSON one — and compare with a constant-time function like timingSafeEqual, never ===, so a failed check can't leak timing information about your secret.

05 Rotating your secret

In the Agent's settings, "Regenerate secret" immediately invalidates the old whsec_ value — every delivery from that moment on is signed with the new one. There's a short cutover window: update the secret stored on your endpoint first, or expect a handful of 401s until you do. Those failures are retried safely on the normal backoff schedule, so nothing is lost — it just arrives a little later.

06 The event envelope

Every delivery is a single JSON object with the same five top-level fields; only payload varies by event type.

07 Events

ping

Fires when an operator clicks "Send test event" in the Agent's settings — never fired automatically. Use it to confirm your endpoint, TLS, and signature verification before any real data flows.

Payload fieldTypeDescription

stock.updated

stock.updated

Fires when a stock item's tracked fields change since the last poll — quantity on hand, unit, sale price, or cost price. One event per changed item.

Newly discovered stock items also arrive as stock.updated — the Agent treats "create" and "update" the same way for stock, so upsert on your side keyed by guid.

Payload is a single Stock item object.

stock.snapshot

stock.snapshot

Fires when an operator triggers a manual full resync from the Agent. Carries the entire stock list in one pass regardless of whether anything changed — useful for rebuilding your catalog from scratch or recovering from drift.

Payload fieldTypeDescription
itemsStock item[]Up to 500 items per event — see Stock item.
chunknumber1-based index of this chunk.
total_chunksnumberTotal chunks in this resync.
Chunking

Large catalogs split into multiple events of up to 500 items each, sent in order. Treat every chunk as additive/upsert — don't assume chunk 1 alone is the whole catalog.

ledger.created / ledger.updated

ledger.createdledger.updated

Fires when a Tally ledger account is first seen (.created), or one of its tracked fields — name, group, GSTIN — changes (.updated).

Payload is a single Ledger object.

voucher.created / voucher.updated

voucher.createdvoucher.updated

Fires when a voucher — invoice, receipt, payment, journal, and so on — is first seen, or its content changes, within the Agent's configured lookback window (90 days by default; see Polling intervals).

Payload is a single Voucher object.

voucher.cancelled

voucher.cancelled

Fires when a previously-seen voucher's cancelled flag flips to true. Same Voucher shape, with isCancelled: true.

There is no separate delete event for vouchers — cancellation is Tally's own supported way to void a voucher, and it's what this event tracks.

09 Delivery & retries

The Agent always attempts its oldest un-delivered event first. Your endpoint must return a 2xx status within 30 seconds for a delivery to count as successful; anything else — non-2xx, timeout, connection error — schedules a retry.

AttemptRetries after
130 seconds
22 minutes
310 minutes
430 minutes
52 hours
6–126 hours (repeats)

After attempt 12 fails, that event is marked failed on the Agent and not retried again — but it does not block later events, which keep being attempted on their own schedule as soon as they're due.

Ordering

Because a failing event's backoff delay doesn't hold up newer ones, delivery is best-effort chronological, not strictly ordered under failure — an event five minutes newer can arrive before one still waiting out a retry. id and created_at in the envelope are enough to reorder on your side if you need to.

Idempotency: retries reuse the exact same id. Store it (or read X-Tally-Event-Id) and treat repeats as no-ops.

10 Responding to events

  • Return 2xx as soon as you've durably queued the event; do the slow part — writing to your own database, calling other services — after responding, so you comfortably clear the 30-second timeout.
  • Any non-2xx is treated as failure and retried on the schedule above. If you understand an event but intentionally don't want to act on it, return 2xx and drop it — a 4xx there just causes the Agent to keep retrying something you'll never accept.
  • The response body isn't read by the Agent; only the status code matters.

11 Polling intervals

Each entity polls and diffs independently, on defaults configurable per install:

Vouchers
every 2 minutes
90-day lookback by default
Stock
every 10 minutes
full item list, diffed
Ledgers
every 30 minutes
full account list, diffed

The Agent keeps a local snapshot of the last known state per record and only emits an event when something actually changed — your system never has to re-derive "what's new" itself.

First run

A fresh install, or switching Tally companies, triggers a silent baseline pass: the Agent snapshots everything it sees but sends no events, so you don't get flooded with thousands of .created events for pre-existing data. Trigger a manual stock.snapshot from the Agent any time you want the full current catalog pushed explicitly.

12 How prices are resolved

Tally doesn't store one canonical "price" per item — the Agent resolves the most representative value it can find, in order, and falls through to the next source if one isn't available.

salePrice

  1. Most recent actual sale, from real sale vouchers
  2. Tally's Standard Price, if set on the item
  3. The item's Standard Price List, if configured
  4. 0, if none of the above are available

costPrice

  1. Tally's Standard Cost, if set on the item
  2. Tally's closing valuation rate
  3. The item's Standard Cost List, if configured
  4. Closing value ÷ closing quantity
  5. Most recent actual purchase, from real purchase vouchers
  6. 0, if none of the above are available
Zero isn't "free"

0 means nothing in this company's Tally data could resolve the field — not that the item's real price is zero. If your system has already stored a nonzero value from an earlier sync, prefer that over a later 0 rather than overwriting good data with an empty one: transaction history available to sync can vary pass to pass (for reasons outside Tally itself, such as licensing tiers that restrict how far back entries are enterable), so one pass finding no signal doesn't mean the value actually changed.

13 FAQ

What happens if Tally is closed or unreachable?

The Agent detects the connection failure, surfaces it in its own status UI, and tries again on the next poll. No events are lost — they're just delayed until Tally is back.

What happens if my endpoint is down for an extended period?

Events queue locally on the Agent and retry on the backoff schedule above, up to 12 attempts spanning roughly 10 hours per event. For longer outages, trigger a stock.snapshot (and review recent vouchers) once you're back, to reconcile anything that aged out of retry.

Can one Tally company send to more than one endpoint?

Not from a single Agent install — one Agent instance targets one webhook URL. Run a second install pointed at a different connection if you need multiple targets.

Does OpsTally store my Tally data anywhere?

The Agent's local database exists only to track what it has already seen, so it can compute diffs, and to queue events until your endpoint acknowledges them. It is not a hosted copy of your books — you receive and own whatever your endpoint stores.

Do I need to poll anything on my side?

No. Delivery is push-based. Your endpoint just needs to be reachable over HTTPS and respond within 30 seconds.
